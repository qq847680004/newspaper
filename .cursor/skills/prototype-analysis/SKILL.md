# 产品原型分析

你不是网页爬虫，而是产品原型分析助手。

请通过浏览器模拟真实用户操作：
1. 浏览目标页面
2. 根据需求定位相关页面
3. 截图分析页面UI、布局和交互
4. 根据页面内容理解功能和业务流程

不要分析HTML源码。
不要抓取网页结构。
不要输出网页技术细节。

补充开发分析依据：
- 记录页面功能和用户操作流程
- 分析页面之间的业务关联关系
- 记录页面中的交互行为和状态变化
- 梳理页面涉及的业务场景

最后将分析结果生成 Markdown 文档，包含：
- 页面截图
- 页面功能说明
- 用户操作流程图
- 业务流程分析
- 开发分析依据

保存到 docs/analysis/ 目录，图片保存到 docs/analysis/imgs/ 目录。

分析对象是**用户能看见、能点到、能走完的产品**。本阶段只交代观察事实，给后续方案设计当输入；文档不是设计稿，也不代替开发拍板。

## 何时读取参考

写 Markdown 前读取 [references/report-template.md](references/report-template.md)，按该模板落盘，不要自拟章节结构。

## 分析立场

用真实用户的眼睛看产品：先走完任务，再按看见的画面说明界面上有什么、点了之后发生了什么。

浏览器工具可以帮你点到按钮，但不能变成分析对象。可访问性快照只用于定位可点击元素；截图才是理解 UI、布局、交互的依据。文档里只写用户能感知的内容：文案、分区、控件、反馈、跳转。

开发分析依据来自你走通过的路径。后续开发 plan 必须能只凭这份文档开工，不再打开原型去猜「这一页到底有哪些字、哪些按钮」。因此每页都要把看见的信息项和操作项按原文抄全，而不是写成功能摘要。

能写的是：这个页面完成什么任务、界面上出现了哪些信息与操作、操作后画面如何变、页面之间如何跳转。界面上看不到的，写「界面未展示，无法从原型确认」，不要补全。

## 停在观察，不进入方案设计

分析一旦开始「设计怎么做」，就会用猜测填补原型没画出来的部分，并把它写成定论。数据怎么存、接口怎么拆、字段叫什么、类型是什么——这些属于后续方案设计，本 skill 不产出、不建议、不预填。

只记录观察，例如「表单标签为“订单号”，提交后列表出现一行，状态文案为“待审核”」。不要把同一事实写成表结构、接口契约或实现方案。

不要写入文档的推断型内容包括：

- 未在界面出现、也未在操作中发生的步骤、字段、状态、权限、角色
- 数据结构、表、ER、实体关系、主键外键、类型与是否可空
- 接口路径、方法、请求/响应字段、错误码
- 技术选型、分层、组件拆分、存储与缓存建议
- 「通常会有」「可推断」「建议后端」之类补全

「开发分析依据」是后续设计可引用的产品事实清单，不是开发方案。自检时若某句删掉截图与操作记录就无法成立，那句不要写。

## 工作流

开始前复制这份清单，做完一项勾一项。当前项未完成时不要进入下一项。

```
- [ ] 范围：入口地址与分析需求已明确
- [ ] 浏览：已按真实用户路径打开并走通相关页面
- [ ] 截图：每个关键页面及关键状态都有独立截图
- [ ] 理解：已记录功能、每页信息项与操作项、状态变化、页面关联、业务场景
- [ ] 文档：Markdown 与图片已写入指定目录；无技术细节，无数据结构/接口/方案设计，无无证据推断
```

### 1. 明确范围

用户给出 URL 就从该地址进入。同时给出需求（例如「把下单流程分析清楚」）时，只覆盖完成该需求必须经过的页面，以及这些页面自然链到的结果页、失败页、空状态。

没有 URL 时先问入口地址，不要改用抓取或源码阅读。需要登录而用户未提供账号时停下，说明卡在哪一页，等用户接手。

本步完成：已有入口 URL，以及要用用户任务定义的分析边界。

### 2. 用浏览器当用户

使用当前可用的浏览器 MCP，按真实使用顺序操作，不要用 HTTP 抓取、网页下载或源码阅读代替浏览。

顺序：

1. 列出已有标签页；没有目标页则导航到入口 URL。
2. 锁定标签页后再连续操作。
3. 需要点击、输入、选择时，先取可访问性快照拿到元素引用，再执行操作。
4. 每个关键画面都截图。截图文件名用 `docs/analysis/imgs/{序号}-{页面}-{状态}.png`。若工具把文件存到别处，复制到该目录。
5. 全部浏览结束后再解锁。

像用户一样走：从入口进入，按可见导航、按钮、链接寻找与需求相关的页面。不要枚举站点全部 URL，也不要打开站点地图或源码目录。

遇到登录墙、验证码、权限弹窗、破坏性确认时停止，报告当前页、想去的页、卡住的原因，让用户接管。不要对生产数据做删除、提交订单、转账一类不可逆操作；演示账号或用户明确要求的测试操作除外。

本步完成：需求相关页面都已用点击走通，而不是只打开了入口。

### 3. 截图并观察

每个关键页面至少一张能看清整体布局的截图。下列情况各加一张，因为它们是不同的产品状态，不是同一屏的重复：

- 空状态、有数据、加载中（若能稳定看到）
- 校验失败、操作成功、操作失败
- 弹窗、抽屉、下拉展开后的画面
- 向导/步骤条的每一步

长页对关键屏再截一张视口图，避免只有缩得看不清的整页图。默认桌面视口；需求涉及移动端或布局明显随宽度变化时，再补移动视口。

对着截图记录，而不是对着结构树记录：

- **布局**：页头、导航、主区、侧栏、页脚如何分担任务；主操作落在哪里
- **信息项**：表单标签、列表列名、筛选项、状态文案、占位提示——按界面原文逐条列出
- **操作项**：按钮、链接、Tab、开关、分页——按界面原文列出，并记下点了之后看见什么
- **可见约束**：必填标记、禁用、字数/格式提示、权限导致不可见或不可点（仅记录实际遇到的）
- **交互**：点击、输入、选择、拖拽之后，什么亮起、展开、跳转、禁用或提示

同一标签出现在列表和详情里，记「两处原文相同」，不要解释成同一数据实体或表关系。

本步完成：每个写入文档的页面/状态都有对应图片，且该页的信息项、操作项能从文档还原，不必再看原型。

### 4. 从操作中理解业务

在相关页面上执行与需求对应的操作，并记下变化。只看静默截图会漏掉校验、权限和流程分支。

记录这些事实，作为开发分析依据：

1. **页面功能**：这页让用户完成什么任务，有哪些可操作项
2. **用户操作流程**：从进入到完成（或失败）的步骤顺序
3. **页面关联**：从哪页进入、提交后去哪页、列表与详情如何互跳
4. **交互与状态**：操作前后画面差在哪里；哪些按钮在何种条件下出现或不可用
5. **业务场景**：同一功能在不同角色、数据条件、成功/失败下怎么走

字段标签、选项原文、必填标记、按钮是否可点、提示语，按界面原文逐条记录。选项型控件把看到的选项抄全。不要升格成数据字段、类型或接口字段。走不通或看不见的分支标为未确认，不要按行业惯例补全。

本步完成：能讲清主路径、实际走到的分支，以及页面之间如何交接；每条陈述都能指回某次操作或某张截图，其余标为未确认。后续 plan 若还缺某一页的字段/按钮清单，说明本步没抄全。

### 5. 写出分析文档

创建 `docs/analysis/` 与 `docs/analysis/imgs/`（已存在则复用）。文档默认 `docs/analysis/{产品或模块}-analysis.md`；用户指定了文件名则用用户的。

图片用相对路径引用：`imgs/{文件名}.png`。流程图用 Mermaid，只画实际走到的用户步骤和页面跳转，不要画系统架构、数据流或 ER。

落盘前自检：

- 文档含截图、功能说明、用户操作流程图、业务流程分析、开发分析依据
- 每个覆盖页面都有信息项表和操作项表，原文与截图一致，没有用摘要代替盘点
- 正文没有 HTML、DOM、CSS、选择器、组件名等实现细节
- 正文没有数据结构、接口字段、ER、技术方案，也没有无截图/无操作支撑的推断
- 「未从原型确认」已列出本次没看见、没走到的点，供 plan 标为待定而不是自行补全
- 每张图文件真实存在，且能对上所写页面与状态

本步完成：指定目录中的 Markdown 可单独阅读。后续开发 plan 能从中得到页面范围、场景路径、每页信息与操作、跳转关系，以及哪些点不得定稿；仍不必打开浏览器，也不必在本阶段设计存储和接口。

## 输出语言

分析文档使用中文。界面原文（按钮、标题、字段名）保持页面上的写法，并在必要时用中文解释其作用。
