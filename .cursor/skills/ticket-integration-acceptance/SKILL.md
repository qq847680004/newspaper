# Ticket 集成测试

## 目标

先排出可顺序执行的 ticket 清单，再把共享同一条数据/状态/页面衔接、可连续开发的多个 ticket **合并成一组**，只在该组最后一张做完后写一条集成验收。单 ticket 由 `/implement` 负责。无跨 ticket 传递的不做验收。后面的验收不重跑前面已通过的链路。前端、后端、同一仓库内的页面与接口都按本规则处理。

## 按项目类型选验收面

读 Spec 后只选与当前仓库相符的面，不要混用未实现的栈：

- **后端**：网关或项目约定的 HTTP/RPC；用已有接口产出的真实数据作为后一 ticket 的输入。
- **前端**：浏览器真实操作（路由、列表、表单、状态、权限展示）；用上一页面/流程留下的数据继续点，不要只用截图。
- **前端 ticket 依赖后端接口**：只验本仓库能控制的衔接（页面是否按契约展示、跳转、提交）；不要在前端仓库里改后端代码，除非用户明确要求全栈。
- **后端 ticket 被前端消费**：只验接口契约与副作用；不要在后端仓库里改前端代码，除非用户明确要求全栈。

外部依赖按 Spec 用 Mock/替身；本轮预留或不实现的能力不作为通过条件。

## 生成规则

1. 读 Spec 和 ticket 的 `Blocked by`、输入、输出、状态或路由变化。
2. 排出 **Ticket Execution Order**：满足依赖、尽量按编号。
3. 把可连续开发、且验收时必须互相消费产出的 ticket 收成一组。后端例：列表查询 + 创建 + 详情围着同一条记录。前端例：列表页 + 新建页 + 详情页围着同一条用户路径。组内中间 ticket 写「做完后无集成验收」，只在组内最后一张写「做完后执行下方集成验收点N」。
4. 跨阶段流转（状态变更、提交后跳转、锁单后再编辑）不要和上一组绑在一起，另开验收项。
5. 每个验收项只测该组新衔接 + 对已有表面的增量副作用（例如列表金额从空变为有值、按钮从可点变为禁用）。禁止把前序组的主路径再跑一遍。
6. 不写「全部 ticket 完成后全链路回归」。
7. 发现 Bug：在当前仓库改代码 → 只回归本项 → 通过后才开始下一组。

## 输出格式

```markdown
## Ticket Execution Order

按此顺序做。单 ticket 用 /implement。同一组可连续开发，做完该组最后一张才做下一节对应项。

1. ticket 01 — [名称]：做完后无集成验收
2. ticket 02 — [名称]：做完后无集成验收
3. ticket 03 — [名称]：做完后无集成验收
4. ticket 04 — [名称]：与 02、03 同一组，做完后执行下方集成验收点一
5. ticket 05 — [名称]：做完后执行下方集成验收点二

## Integration Acceptance Flow

只在一组相关 ticket 都做完后验一次。用已有数据/页面往下走。未通过不得开始下一组。发现 Bug 立即修并只回归本项。

### 集成验收点一：ticket 04 后

完成 ticket 02、03、04 后：[组衔接名称]。

给 AI 的步骤：

1. `请用本组产出只验跨 ticket 衔接，不要重跑各 ticket 的 /implement 主路径。`
2. `发现 Bug 立即在当前仓库改代码，只回归本项，通过后再做后续 ticket。`

### 集成验收点二：ticket 05 后

完成 ticket 05 后：[新阶段衔接名称]。

给 AI 的步骤：

1. `请用上一组已有数据或页面只验本阶段新行为；已验收项不要重跑，只核对本段增量。`
2. `发现 Bug 立即在当前仓库改代码并只回归本项，通过后再做后续 ticket。`
```

## 约束

- 标题用 `Ticket Execution Order` 和 `Integration Acceptance Flow`。
- 验收项标题固定为 `### 集成验收点N：ticket XX 后`，衔接说明写在标题下一行。
- 验收点数应明显少于 ticket 数；能合并的同一闭环不要拆成逐步验收。
- 执行顺序从上往下看，只有「执行下方集成验收点N」的行才停下来做集成验收。
- 步骤里写清验收面（接口或页面），不要默认全是 HTTP，也不要默认全是 UI。
- 后面的步骤禁止写「重新执行 ticket 01～N 完整链路」。
- 不把预留/不实现能力写成通过条件。
- 不修改 Spec/ticket 原文要求；冲突则停下说明。
