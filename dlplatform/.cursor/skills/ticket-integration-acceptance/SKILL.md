# Ticket Execution and Integration Acceptance

## 目标

从当前 Spec 和已有 ticket 原文生成两个可直接执行的章节：先给出满足依赖的 Ticket Execution Order，再将共享真实数据、状态或用户路径的 ticket 合并为少量 Integration Acceptance Flow。单 ticket 的功能正确性由 `/implement` 负责；本 skill 只验证跨 ticket 的衔接和新增副作用。

## 按项目类型选验收面

读 Spec 后只选与当前仓库相符的面，不要混用未实现的栈：

- **后端**：网关或项目约定的 HTTP/RPC；用已有接口产出的真实数据作为后一 ticket 的输入。
- **前端**：浏览器真实操作（路由、列表、表单、状态、权限展示）；用上一页面/流程留下的数据继续点，不要只用截图。
- **前端 ticket 依赖后端接口**：只验本仓库能控制的衔接（页面是否按契约展示、跳转、提交）；不要在前端仓库里改后端代码，除非用户明确要求全栈。
- **后端 ticket 被前端消费**：只验接口契约与副作用；不要在后端仓库里改前端代码，除非用户明确要求全栈。

外部依赖按 Spec 用 Mock/替身；本轮预留或不实现的能力不作为通过条件。

## 生成前检查

1. 只使用 Spec 中已存在的 ticket；没有编号或名称的工作项不得自行编造 ticket。
2. 为每个 ticket 提取：编号、名称、`Blocked by`、输入来源、产出、状态变化、路由或接口变化、验收面、明确的 Mock/预留范围。
3. 检查依赖是否形成环；有环、缺失依赖、重复编号或 ticket 原文冲突时停止生成，并指出具体冲突。
4. 将依赖中的“完成”理解为对应 ticket 的 `/implement` 已通过，不把集成验收结果倒灌成 ticket 依赖。
5. 以 Spec 为唯一依据；Spec 与计划、ticket 或现有末尾章节不一致时，采用 Spec 的明确要求，并保留未解决冲突供用户处理。

## 生成规则

1. 对 ticket 依赖做拓扑排序；无依赖的 ticket 按 Spec 出现顺序，其他并列 ticket 按编号排序。顺序必须让每个 `Blocked by` 出现在被依赖 ticket 之后。
2. 识别跨 ticket 衔接：后一 ticket 必须消费前一 ticket 产出的真实记录、状态、接口响应、页面数据或路由上下文，且两者在当前仓库可验证。
3. 将同一闭环中可连续开发的 ticket 合并为一组。列表/统计/详情围绕同一记录、创建/查询围绕同一数据、页面/接口围绕同一用户路径可合并。
4. 跨状态阶段、锁定后行为、提交后行为、文件或副作用边界必须拆组；不能因共享同一条记录而强行合并。
5. 组内除最后一个 ticket 外均标记“做完后无集成验收”；组末 ticket 标记“做完后执行下方集成验收点N”。没有跨 ticket 衔接的 ticket 标记“做完后无集成验收”。
6. 每个验收点只覆盖组内新衔接，以及已有页面或接口的直接增量副作用；必须注明接口、页面或两者验收面。
7. 每个验收点必须给出：前置数据/来源、操作顺序、关键断言、失败后动作。关键断言至少包含状态、数据是否落库或可见、权限/数据范围、文件/缓存/外部调用等 Spec 明确要求。
8. 后续验收复用前一组已通过的真实数据或页面上下文，不重跑前序主路径；如必须新建数据，说明原因和最小准备步骤。
9. 不把 Mock、预留、不实现能力写成通过条件，不写“全部 ticket 完成后全链路回归”。
10. 验收点数量应明显少于 ticket 数；只有无法合并的阶段边界才新增验收点。

## 输出格式

只输出当前 Spec 缺少的章节，不输出额外解释。分别检查 `## Ticket Execution Order` 和 `## Integration Acceptance Flow`：标题已存在的章节不生成、不删除、不覆盖；标题不存在的章节才生成，并将其写入当前 Spec 最末尾。

## Ticket Execution Order

按此顺序做。单 ticket 用 `/implement`。同一组可连续开发，做完组末 ticket 后才执行对应验收点。

1. ticket XX — [名称]：做完后无集成验收
2. ticket XX — [名称]：与 XX 同一组，做完后执行下方集成验收点一
3. ticket XX — [名称]：做完后执行下方集成验收点二

## Integration Acceptance Flow

只在对应组的 ticket 全部完成后验收。未通过不得开始下一组。每个验收点固定使用以下结构：

### 集成验收点N：ticket XX 后

完成 ticket XX（以及同组 ticket XX、XX）后：[跨 ticket 衔接名称]。

验收面：接口 / 页面 / 接口与页面。

前置数据：复用 [来源 ticket/验收点] 产出的 [记录/页面/响应]；如无可复用数据，说明最小准备动作。

步骤：
1. [按真实接口或页面顺序执行，只写本组跨 ticket 衔接。]
2. [核对关键增量断言：状态、字段/列表/详情、权限或数据范围及 Spec 要求的副作用。]
3. [核对本轮明确的 Mock/预留边界未被误判为实现。]

通过条件：[可观察的结果]。

失败处理：在当前仓库修复后只回归本验收点；通过后再开始下一组。

## 约束

- 标题用 `Ticket Execution Order` 和 `Integration Acceptance Flow`。
- 验收项标题固定为 `### 集成验收点N：ticket XX 后`，衔接说明写在标题下一行。
- 验收点数应明显少于 ticket 数；能合并的同一闭环不要拆成逐步验收。
- 执行顺序从上往下看，只有「执行下方集成验收点N」的行才停下来做集成验收。
- 步骤里写清验收面（接口或页面），不要默认全是 HTTP，也不要默认全是 UI。
- 后面的步骤禁止写「重新执行 ticket 01～N 完整链路」。
- 不把预留/不实现能力写成通过条件。
- 不修改 Spec/ticket 原文要求；冲突则停下说明。
